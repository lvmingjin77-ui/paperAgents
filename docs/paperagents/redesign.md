# PaperAgents 整体改造方案

日期：2026-11-05　状态：设计稿第 3 版已在 paperAgents02 实现（真实科研验收待运行）　范围：构思、实验、写作三阶段的整体结构

> 依据：[ScientistTwo 分析笔记](scientisttwo-notes.md)。本方案不以 AI-Scientist-v3 为范式。

## 1. 为什么改

本次 `cir-reliability` 运行约 40 worker 小时，投入分布如下：

- 知识准备约 71%（其中逐篇阅读占 54%）；
- 实验前讨论约 29%；
- 实验和写作为 0。

主要问题：

- 三段之间靠导出文件交接，论证、实验、解释、写作无法相互修正；
- 效果在实验前被反复争论，系统趋于保守，瓶颈被提前预设；
- 只有一个 idea 进入实验，没有消融、写作和实验型反驳；
- 输入把科学内容、旧流程描述、非约束线索和资源约束混写在 research.md 里。“优先考虑 i-CIR”等线索被读成了优先级；算力（Apple M4、16 GB、本机执行）没有被系统结构化地使用；
- 角色只覆盖知识与讨论，缺少工程、独立判定和论文评审。

仓库体量也失衡：PaperAgents 自身约 4.9k 行，却背着整套 v3 上游——`src/` 约 12.8 万行，测试约 9 万行，另有 `examples/`、`apps/`、`configs/` 与 v3 文档。主链真正用到的只有 `src.investigation` 中的两处调用。

**目标**：输出会议 LaTeX 论文。每条主张都有实测证据，方法与代码一致，引用真实。保留 PaperAgents 的两个长处：多专家跨论文迁移；实验前的有效性把关。

## 2. 定位：问题驱动

ScientistTwo 是方法驱动的：给定一个 SOTA 方法，找短板，把它改强，产出多为增量改进。PaperAgents 是问题驱动的：先弄清问题难在哪里，再从中提出创新，并用实验验证和塑造这些创新。

**强基线是衡量标准，不是改进对象。**

- 所有 idea 都在同一个评测底座上与强基线比较；
- 但 idea 不必建立在基线之上。

**贡献类型**（候选的 `kind` 字段）：

| 类型 | 含义 |
| --- | --- |
| `enhancement` | 在已有方法上改进 |
| `mechanism` | 新的判定或表示机制 |
| `reformulation` | 重新建模问题 |
| `analysis` | 诊断与分析，例如回答瓶颈在哪、现有方法是否已足够 |
| `baseline` | 作为对照，不作为创新主体 |

**论文可以在三个层面产出贡献**：

1. 问题：新的任务设定与评测底座；
2. 解释：瓶颈诊断及其原因；
3. 机制：针对瓶颈的新方法。

所有机制都无法超过强基线时，产出以问题与诊断为主的分析型论文。这是有效结论。

## 3. 改造原则

1. **替换单元同提交完成。** 新模块上线与旧模块退出放在同一次提交中完成，每次提交都能完整运行。不平行保留新旧两套。
2. **不留兼容层，不写兜底。**
   - 旧运行保留在磁盘上可读，但不续跑、不迁移；
   - 不保留旧格式分支、旧阶段别名和 legacy 导出；
   - 契约只在边界校验一次，内部不重复检查，不为假想错误写兜底路径。
3. **一个共享研究状态。** 主张、证据、运行、草稿是同一张图，论文是它的视图。
4. **证据门控。** 科学结论只由证据决定，不由讨论票数决定。
5. **生成性讨论放开，评判性讨论交给证据。**
   - 专家之间可以自由提出、延伸、组合、反驳想法；
   - “有没有效”由实验回答；
   - “能否有效检验”由批评者依据有效性规则和资源判断。
6. **先独立，后交流。** 保护提案的多样性。
7. **三层嵌套循环，每层可回退。** 方向、idea、实现三层，后续环节的否定性证据都能把主张退回作者修订。
8. **专家贯穿全程。** 同一位专家负责提出、诊断、撰写、反驳。
9. **统一控制原语。** 每一步都是“产出者 + 批评者 + 有上限循环”。协调器只管状态、预算、回执，不做科学裁决。
10. **资源决定规模，不决定价值。**
    - 评测底座、筛选数量由声明的资源推出；
    - 超出资源的方案标为“当前资源无法验证”，保留其研究价值和所需资源说明；
    - 预算耗尽记为“预算内未完成”，不等同于实现失败或机制失败。
11. **简洁而非限额。** 控制代码量的目的是不写防御性兜底、不堆叠冗余结构，而不是设硬性行数上限。按模块估算规模，整体净下降；运行器、写作、底座等必要功能完整实现，不为压缩行数偷工。

## 5. 输入

项目输入只有两个文件和一个可选目录。系统流程不写进输入。

### 5.1 research.md：只写科学内容

固定五节，由 `init` 生成模板：

1. **问题与范围**：研究问题、示例、不研究什么。
2. **任务定义与指标**：形式化定义、主要指标、工作点、统计要求。
3. **评价有效性规则**：数据构造、划分、泄漏、可比性等必须满足的条件。底座审查逐条核对。
4. **开放问题**：需要实验回答的问题。领域全景按这些问题组织，选队和提案都不得预设答案。
5. **非约束性线索**：文献、数据、代码入口，固定标注“仅供调研，不代表优先级或技术路线”。

研究闭环、预期交付等流程描述删除，由系统定义；资源与运行安排移入 toml。

### 5.2 paperagents.toml：结构化配置，由程序读取

| 节 | 字段 | 用途 |
| --- | --- | --- |
| `[resources]` | `device`、`memory_gb`、`gpu`、`wall_clock_days`、`api_budget` | 底座规模、可验证性判断、预算分配 |
| `[data]` | `allowed_sources`、`download`、`license_notes` | 数据获取与构造的边界 |
| `[loops]` | `screen_top_n`、`exploratory_slots`、`evolve_rounds`、`target_good`、`engineering_budget`、`seeds`、`max_candidates_per_expert` | 中层与内层预算 |
| `[output]` | `venue`、`template`、`page_limit`、`anonymous` | 写作通道 |
| `[checkpoints]` | `testbed`、`final_method`、`submission` | 人工检查点；为 true 时暂停等待确认 |
| `[research]` | `lookback_years`、`core_papers`、`allow_temporary_experts` | 保留 |
| `[glm]`、`[execution]` | — | 保留 |

删除 `[discussion]` 节，以及 backend 中的 `command`。

### 5.3 inputs/（可选）

存放用户已有的数据、代码、权重、论文。知识准备和底座构建阶段优先使用；协调器记录哈希，作为证据来源。

### 5.4 cir-reliability 的迁移

- 按 5.1 重组 research.md；
- 资源写入 `[resources]`：M4、16 GB、集成 MPS（无独立 GPU）、本机执行；
- i-CIR、CIRR 移入“非约束性线索”，其使用约束保留在有效性规则中；
- 新建运行，不续跑旧运行。

## 6. 角色

按职能设四类角色，每类可有多个实例；不按阶段拆分 agent。

| 角色 | 实例 | 职责 | 独立性规则 |
| --- | --- | --- | --- |
| 专家 | 领域专家、论文（方法）专家、临时专家 | 知识、提案、交叉意见、失败解释、撰写章节、反驳论证。领域专家另兼：讨论引导者（指出领域全景中无人提案的开放问题，不裁决）、主编（叙事与 LaTeX 统稿） | 不判定自己的主张 |
| 工程师 | 按任务派生 | 获取与构造数据、实现方法、调试、执行消融与补充实验 | 不提交分数，分数只由运行器产生；不修改主张 |
| 批评者 | 按判定派生，与作者隔离 | 协议有效性、idea 的可检验性与资源可验证性、六维评估、运行判定、代码与方法一致性、查新 | 只判定，不写方法和代码 |
| 评审团 | 多位审稿人 + meta-review | 论文评审，决定定稿、退回或降级 | 不参与写作 |

**由协调器程序完成、不用 agent 的部分**：分数计算、数字宏生成、引用来源核对、LaTeX 编译、预算与进度推进。

**现有角色的去向**：

- `researcher` 拆入专家（知识任务）与工程师（数据和实现）；
- `verifier` 扩展为批评者；
- 主持人与综合者删除。去重由批评者初筛加作者确认完成；主方法定稿由领域专家依据证据提出，再经批评者核对。

## 7. 共享研究状态

每次运行一个 `state/` 目录，协调器是唯一写入者。共四类对象：

| 对象 | 关键字段 | 说明 |
| --- | --- | --- |
| Claim 主张 | `claim_id`、`version`、`kind`、`text`、`owner`、`parents`、`verdict`、`stage`、`evidence_ids` | 论文中可检验的陈述都来自主张；任何科学内容的修改都生成新版本 |
| Evidence 证据 | `evidence_id`、`kind`（literature / run / diagnosis / assessment / review）、`claim_ref`（`claim_id@version`）、`source`、`hash` | 证据绑定到具体主张版本 |
| Run 运行 | `run_id`、`claim_ref`、`protocol_id`、代码清单哈希、`split`、`seed`、`metrics`、`outcome` | 不另设实现对象，实现由代码哈希表示 |
| Draft 草稿 | LaTeX 章节；段落标注 `claim_ref`；数字为由证据生成的宏 | 不手抄数字 |

**两个独立字段，不混用：**

- `verdict`（科学结论）：`untested`、`supported`、`refuted`、`inconclusive`、`unverifiable_with_resources`。只由证据改变。
- `stage`（工作进度）：`proposed`、`exchanged`、`screening`、`confirming`、`novelty`、`ablation`、`frozen`、`tested`、`written`。由流程推进。

**运行结果 `outcome`**：`completed`、`impl_failed`、`protocol_failed`、`budget_exhausted`。批评者依据与主张相匹配的有效证据判断 `verdict`：完成且协议有效的运行才可作为效果证据；运行完成不代表支持或反驳，样本不足或结果不明确记为 `inconclusive`。文献可支持或反驳文献性主张；诊断、评分和评审本身不能证实效果。资源评估可标记 `unverifiable_with_resources`。其他运行结果记为工程或资源事实。

被反驳的主张不删除，保留为负面结果或局限。现有的候选谱系、哈希回执、阅读锚点并入这张图。

## 8. 三层循环

### 8.1 外层：方向（天）

- **K1 知识准备**：scope → corpus → reading → domain → selection → 方法与临时专家（审查，必要时修订一次）→ 领域专家（逐条回应纠正，发布修订后的全景）。
  - reading 产出论文卡与覆盖记录；深读只对入选的核心论文，在 expert 阶段进行；
  - 领域全景按开放问题组织，选队先比较竞争路线与团队组合（均已实现）。
- **K2 评测底座**（专家设计，工程师执行）：
  - 按 `[resources]` 与 `[data]` 确定规模；
  - 数据划分为开发子集、开发全集、封存测试三份；
  - 定义指标与种子数，复现强基线；
  - 记录可观测的失败现象、有证据支持的归因、竞争解释和尚未区分的部分；召回、感知、联合判断、接受决策仅是 CIR 的示例，允许原因重叠和未知，不要求先得到各自的失败比例；
  - 开发子集要能在资源预算内支撑一批 idea 的筛选。
- **K3 协议审查**（批评者）：逐条核对 research.md 的有效性规则，包括标签、泄漏、划分独立性、统计前提。
  - 审过的公共协议记为 `protocol_id`，可被后续运行复用；
  - 新方法引入新的数据处理、标签使用或评价方式时，对变化部分再审；
  - 不通过则回到 K2；问题框定被证据推翻则回到 K1。

### 8.2 中层：idea（小时）

1. **I1 独立提案**：专家依据领域全景、实测诊断与自身方法知识密封提案，标注 `kind`。
2. **I2 交流**：见第 9 节。所有专家阅读全部提案并给出交叉意见，作者修订一次。
3. **I3 去重**：批评者初筛归组，作者确认合并、撤回或说明差异（已实现的 triage / merge）。
4. **I4 可检验性评估**（批评者）：
   - 判断能否有效检验、当前资源能否验证；
   - 给出六维评估（第 11 节）；
   - 无法有效检验的退回作者，资源无法验证的标为 `unverifiable_with_resources` 并保留。
5. **I5 组合选拔**：选出进入筛选的一批，覆盖不同开放问题和 `kind`，并含 `exploratory_slots` 个探索名额；不只取最有把握的几个。
6. **I6 子集筛选**：工程师实现，运行器执行，批评者判定。
   - **有希望**：进入确认阶段；
   - **无效**：`verdict=refuted`；
   - **待工程**：进入内层，预算用完记为 `budget_exhausted`。
7. **I7 解释**：提出者解释结果，其他专家可补充竞争解释。解释相互冲突时，设计判别实验。
8. **I8 修订与进化**：专家依据全部成败证据修订自己的候选，或通过交流生成组合与新候选，回到 I4。满 `evolve_rounds` 轮或得到 `target_good` 个通过确认的主张时停止；全部失败且解释指向问题框定时，回到外层。
9. **I9 全集确认**：用新种子在开发全集上验证，用于抵消子集筛选中的“赢家诅咒”。失败则退回 I8 修订。
10. **I10 查新**：只对确认通过的主张做深度查新。发现撞车时退回 I8，由作者收窄、修改或撤回。
11. **I11 消融**：逐组件归因并删除无效组件。若消融否定了核心机制，退回 I8；若只删减组件，生成新版本，重新在开发全集上确认。

**每个阶段的“通过”只代表获得继续验证的资格，不是终点。** 全集确认、查新、消融的否定性结果都通向作者修订或主张降级。

### 8.3 内层：实现（分钟）

工程师实现 → 运行器执行 → 工程师调试，以 `engineering_budget` 为上限。批评者核对代码与对应主张版本是否一致。

## 9. 讨论机制

**生成性讨论**（放开）：

- **I2 交流**：每位专家阅读全部提案后，可以做四件事：
  - 延伸：在他人提案上加入自己的机制；
  - 组合：跨论文迁移，组合成新方案；
  - 反提案：对同一现象提出竞争解释及方法；
  - 指出问题：写明理由与可检验的影响。
- **作者回应**：作者阅读针对自己提案的交叉意见，修订一次（保留谱系），或说明不采纳的理由。只有一轮，不设多轮辩论。
- **探索名额**：每位专家可提一个不受实测诊断约束的高风险想法，标为探索性。
- **引导者**：领域专家指出领域全景中哪些开放问题还没有提案，不裁决。
- **实验后**：I7 的解释和 I8 的进化同样开放给所有专家，他人的失败可以成为自己的线索。
- **数量上限**：`max_candidates_per_expert` 只限制每位专家最终进入 I4 的数量，不限制交流内容。

**评判性讨论**（交给证据）：

- 效果是否成立：由运行回答；
- 能否有效检验、资源能否验证：由批评者回答；
- 解释冲突：转为判别实验。

## 10. 写作与评审通道

| 步骤 | 时机 | 内容 |
| --- | --- | --- |
| W0 骨架 | K3 通过后 | 会议 LaTeX 模板；问题、相关工作（来自领域全景与语料 bib）、实验设置 |
| W1 增量更新 | 主张版本或结论变化时 | 负责专家改写对应段落；数字宏只引用开发集证据 |
| W2 开发集初稿 | 中层停止后 | 基于开发集结果写完整初稿，包括方法、分析、局限（含被反驳的主张） |

## 第二轮修正（2026-11-09）

依据：对正在运行的 `cir-reliability`（知识阶段，59 张阅读卡，87 次 worker 调用）的检查、与 AI Scientist-v2、DeepScientist、InternAgent、Kosmos 等系统的对比，以及 Codex 的复核。结论：控制流程基本完整；最薄的是“什么实验能证明什么结论”的约定，以及把论文理解转化为有效实验的能力。扩大候选数量、调试次数之前，先把这两件事做可靠。

### R1 多基线

协议的 `programs` 除主基线 `baseline` 外，可声明任意多个命名基线（强验证器、标准校准等）。基线诊断、每次比较、最终测试都运行全部基线；候选与每个基线分别比较。`kind=baseline` 的主张不再承担对照职责。

### R2 数据与统计约定

- 评测程序除 `metrics.json` 外，必须输出 `units.json`：`{统计单位: {指标: [分子, 分母]}}`。统计单位是协议声明的独立单位（`statistical_unit`，如原始实例组），不是单条查询；同一实例派生的多个图库属于同一单位。
- 协议指标须能写成“分子之和 / 分母之和”。运行器用 `units.json` 独立重算指标，与 `metrics.json` 不一致记为 `protocol_failed`。
- 比较按统计单位做配对 bootstrap，给出候选、各基线及差值的区间。样本不确定性（单位重采样）与算法随机性（种子）分开报告；确定性方法不必为凑数重复种子。
- 比较结果作为 `comparison` 证据保存，论文可用宏引用汇总值，不再只能引用单次运行。

### R3 资格、运行结果、科学结论三层分开

- **运行结果**：`completed`、`impl_failed`、`protocol_failed`、`budget_exhausted`，只描述执行。
- **资格（gate）**：`advance`、`stop`、`engineer`，只决定是否进入下一阶段。
- **科学结论（verdict）**：针对主张的预测，由批评者综合该版本的有效证据判断。

规则：

- 子集筛选只给资格，结论只能是 `inconclusive`、`refuted` 或不变，不能记为 `supported`；
- 补充实验、消融变体只产生证据和资格，不直接改写主张结论；补充实验完成后，由批评者综合全部证据重新判定；
- 每次判定都写明检验的是哪条预测（`prediction_tested`）。

### R4 方法说明

候选入选筛选后、首次实现前，由作者专家写方法说明（输入输出、组件、步骤、可调参数）并绑定到该主张版本。工程师据此实现，实现审查据此核对代码与方法是否一致。未入选的早期想法不写方法说明。

### R5 文献缺口不再被静默跳过

- 补检索单独计数（`loops.literature_rounds`），不再占用方向轮数（`outer_rounds` 只用于重新定义问题）；
- 有缺口且有额度时补检索，只检索与阅读新增论文；
- 额度用完或已到停止条件时，缺口记入 `unresolved_gaps` 并写入事件，作为已知局限交给写作和评审，不再丢弃。

### R6 选队的路线覆盖

覆盖表每条路线写明 `method_owner`：负责方法的专家，没有则留空。覆盖表中的专家必须是入选专家。没有方法专家的路线作为“未覆盖路线”交给所有专家的提案阶段。判断标准是团队是否真正覆盖了不同的主导机制，而不是备选团队的数量。

### R7 逻辑修正

- 已筛选过的主张版本不再被重复选中；未改动的主张版本不再每轮重复评估；
- 专家的解释只绑定到它明确指向的主张；
- 最终稿生成后，由批评者核对摘要、正文、图注是否忠实于最终证据，重点检查局部结果是否被写成普遍结论；不通过则带意见重写，有上限。

### R8 预算与并发

- 时间预算只计实际运行时间，等待人工确认与暂停不计入；
- `max_worker_calls` 默认提高到 600；
- 互不依赖的 worker 任务（逐篇阅读、专家构建与审查、逐位专家的提案 / 交流 / 修订 / 合并 / 解释 / 进化 / 写作 / 反驳、逐个候选评估、各位审稿人）按 `execution.max_parallel`（默认 4）并发。实验执行仍串行，待实测单次实验的内存与时间后再定。

### 审查补正

- 所有重采样结果相同（例如每个单位都是零事件）时，区间记为空，不报告零宽区间；
- 只有每个指标都分辨出差异时才称“占优”，任一指标未分辨即为 `unresolved`，未检出恶化不等于非劣；
- 抽检样本只能来自开发单位，避免向工作 agent 泄露封存测试标签；
- 并发只启动预算付得起的调用；中断时排队的调用不再启动，运行中的调用连同进程组一起停止；
- 专家的回复按顺序校验并立即生效，同批专家之间的 ID 冲突变成可重试的错误；
- 结论更新在校验阶段试写一次，通过校验的回复一定能记录；只有完成的运行能让候选晋级；
- 比较证据记录它所依据的运行 ID。

### 暂缓

以下在完成一次小规模真实闭环、实测成本后再定：按决策组织阅读（广读识别路线，深读服务于任务定义、评价有效性、强基线、最近邻与待实现机制，补读须说明会改变哪个决定）；筛选数量与进化轮数；实验并发。最后用相同预算对比“普通研究 agent”与“加入论文专家的 PaperAgents”，检验专家设计的实际增益。

## 纠错回传（2026-11-10）

依据：`cir-reliability-e2e` 的真实运行中，规则已经写明却没有被执行，或者纠正没有传回上游。
- 领域全景在只有语料内检索的情况下宣称“领域级空白”；
- FBCIR 专家的审查指出“训练负例比例”不等于“测试图库组成”，领域全景和选队理由仍保留旧说法；

原因在数据流：领域全景和选队写在专家构建之前，专家与审查的发现没有路径回到上游；审查也没有区分“错误”和“边界”。

调整：
- 知识缺口标注范围：`corpus` 是默认值；`field` 必须写出语料外的检索依据。只有 field 缺口能作为创新空间的依据，而且只说明“没找到”。
- 方法与临时专家先构建并审查。来源与领域全景或选队矛盾的论断写入 `upstream_corrections`，由独立审查逐条核对。
- 审查区分 `errors`（与来源不符，必须修正）和 `limitations`（正确知识的边界）。有 error 或阻塞问题时，作者带着审查意见修订一次后再审；仍不通过则暂停。
- 领域专家最后构建，对每条已核实的纠正给出 applied 或 rejected 的回应，并据此发布修订后的领域全景和选队理由。它的审查核对回应是否真正落实、field 缺口的依据是否成立。
- 纠正使队伍不再成立时（`team_valid=false`），自动做一次领域修订并重新选队；同一外层轮次内第二次仍不成立则暂停，交给人决定。
- 所有任务的上下文都能看到每位专家的 `permitted_uses` 与 `limitations`，不只是专家本人。
- 消融计划的每个变体写明要排除的竞争解释（`rules_out`）。计划在看到消融结果前写定，事后新增的分析标为探索性。
- 补充具体操作指导，不设行数目标：领域综合（缺口范围、纠正传播）、专家构建（上游纠错）、专家审查（错误与局限）、选队（依据来源）、提案（从诊断到机制、两句话说清、最强反对意见、AI 式拼接的反例）、消融（用竞争解释组织）。

代价：领域专家改为最后构建，知识阶段多一段串行等待；被拒专家多一次修订。

不采纳：
- “审稿分数提高才保留改稿”：修正夸大结论后，模型评分不一定提高；
- 默认锦标赛排序并删除首轮交流：两两比较替代不了可检验性检查，首轮交流能发现致命假设和重复方案。

后续顺序：先用 `revise --from domain` 检验以上三类错误是否被纠正；再跑通真实底座与基线诊断；之后按实测成本决定筛选宽度、写作调整、图表检查和实验记忆。

## 流程通读修正（2026-11-10）

按“底座 → 提案 → 实验 → 写作”通读代码，修正四处逻辑问题：
- **消融会更新结论。** 以前消融只决定主张能否进入 confirmed，不改变 verdict；消融推翻机制时，主张仍显示 supported。现在消融审查后做一次综合重估（`_reassess`）。
- **先补文献，再进化。** 以前进化轮先提出新版本，再去补读文献，新文献要到下一轮才用得上。现在缺口需要补读时先更新知识，再回到进化轮，带着新文献提案，之后进入全员交流。
- **先定论证，再写正文。** 写作前由领域专家写定 `argument`：问题、证据支持的回答、每条贡献和分析对应的主张版本与证据编号、负结果与限制。协调器核对证据编号确实属于所列主张。各节写作、审稿和定稿都以它为依据；审稿后补做的实验写成补充分析。
- **审稿记录实际检查了什么。** `peer_review` 必须列出实际打开的文件（实现、receipt、日志、units、论文源文件）及发现，路径要真实存在；meta-review 据此权衡意见。

写作 skill 补充了论证优先的写法和“AI 式写法”的具体信号与改法；审稿 skill 补充了整条链的核对要求。

已知缺口，下一步处理：论文中的图表目前只有每次比较自动生成的估计与区间图，无法按分析问题产出分组结果、曲线或误差分解。需要“分析程序”：工程师编写只读运行结果的分析脚本，协调器在沙箱中执行，产出的数字和图进入可追溯目录。

### 本地复审与分析程序的边界

本地复审补齐数据流和契约问题：
- 领域专家返回完整修订后的选队记录，包含成员理由、职责和路线覆盖；只改总理由会让旧错误继续传给下游。同一队伍的身份与来源保持一致，换队通过有界重选完成。
- 补读阶段可以因已核实的纠正重新选队，保留当前协议和主张。领域审查同时收到原纠正及来源，能够逐条核对回应。
- 人工 `revise --from domain` 允许在知识阶段或底座尚未批准时返回知识阶段；底座规划、构建和审查使用新的知识修订标识，不复用旧请求或重试次数。已批准协议后的人工修改仍需从知识/底座重新修订。
- 论证中的每个主张版本都必须有绑定该版本的证据；基线证据可以用于对照，但不能代替候选自己的证据。
- 审稿检查记录必须指向本 run 内的实际文件，并引用存在的主张版本。目录存在不能充当文件检查；这些校验也不等于证明审稿人理解正确。

`confirmed` 表示经过确认与消融审查、可供成文考虑的主张；科学结论仍由 `verdict` 表示，负结果不因此被排除。补实验会在新的 cycle 中重新判读，不能按“只有 supported 才能写论文”合并这两个概念。

分析程序是下一步独立改动，不按代码行数估算完整性：
- 先确认所需观测已经保存。当前 `units.json` 只有各独立单位的指标分子、分母；风险—成功率曲线还需要逐条分数、标签及单位映射，分组分析需要组别。缺少这些输出时先补评测器的输出约定，不能让分析脚本猜测或重新运行模型。
- 只输入明确列出的、已完成的开发运行输出；复用沙箱、日志和超时机制，不调用会重新构建和执行候选的 `_measure`。
- 保存脚本与参数、来源 run/claim 版本及输入输出哈希。派生数字与图引用原始证据，不增加独立样本数，不覆盖原始结果。
- 实验前计划的分析与看过结果后提出的探索分析分开记录。分析发现需要改方法或重新测量时，回到实验流程；封存测试不用于探索分析。
- 数字接入 `metric_catalog`、图接入图表目录，并保留统计单位、适用范围与探索性质。图表能编译不代表布局或科学表达已通过检查。

以上通过合成数据与模拟 worker 验证控制流程；来源理解、真实标签、基线表现和完整研究质量仍需实际运行检验。
