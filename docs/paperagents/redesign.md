# PaperAgents 整体改造方案

日期：2026-11-05　状态：设计稿第 3 版（已纳入 Codex 审查）　范围：构思、实验、写作三阶段的整体结构

> 依据：[ScientistTwo 分析笔记](scientisttwo-notes.md)。本方案不以 AI-Scientist-v3 为范式。

## 1. 为什么改

本次 `cir-reliability` 运行约 40 worker 小时，投入分布如下：

- 知识准备约 71%（其中逐篇阅读占 54%）；
- 实验前讨论约 29%；
- 实验和写作为 0。

主要问题：

- 三段之间靠导出文件交接，论证、实验、解释、写作无法相互修正；
- 效果在实验前被反复争论，系统趋于保守，瓶颈被提前预设；
- 只有一个 idea 进入实验，没有消融、写作和实验型反驳；
- 输入把科学内容、旧流程描述、非约束线索和资源约束混写在 research.md 里。“优先考虑 i-CIR”等线索被读成了优先级；算力（Apple M4、16 GB、本机执行）没有被系统结构化地使用；
- 角色只覆盖知识与讨论，缺少工程、独立判定和论文评审。

仓库体量也失衡：PaperAgents 自身约 4.9k 行，却背着整套 v3 上游——`src/` 约 12.8 万行，测试约 9 万行，另有 `examples/`、`apps/`、`configs/` 与 v3 文档。主链真正用到的只有 `src.investigation` 中的两处调用。

**目标**：输出会议 LaTeX 论文。每条主张都有实测证据，方法与代码一致，引用真实。保留 PaperAgents 的两个长处：多专家跨论文迁移；实验前的有效性把关。

## 2. 定位：问题驱动

ScientistTwo 是方法驱动的：给定一个 SOTA 方法，找短板，把它改强，产出多为增量改进。PaperAgents 是问题驱动的：先弄清问题难在哪里，再从中提出创新，并用实验验证和塑造这些创新。

**强基线是衡量标准，不是改进对象。**

- 所有 idea 都在同一个评测底座上与强基线比较；
- 但 idea 不必建立在基线之上。

**贡献类型**（候选的 `kind` 字段）：

| 类型 | 含义 |
| --- | --- |
| `enhancement` | 在已有方法上改进 |
| `mechanism` | 新的判定或表示机制 |
| `reformulation` | 重新建模问题 |
| `analysis` | 诊断与分析，例如回答瓶颈在哪、现有方法是否已足够 |
| `baseline` | 作为对照，不作为创新主体 |

**论文可以在三个层面产出贡献**：

1. 问题：新的任务设定与评测底座；
2. 解释：瓶颈诊断及其原因；
3. 机制：针对瓶颈的新方法。

所有机制都无法超过强基线时，产出以问题与诊断为主的分析型论文。这是有效结论。

## 3. 改造原则

1. **替换单元同提交完成。** 新模块上线与旧模块退出放在同一次提交中完成，每次提交都能完整运行。不平行保留新旧两套。
2. **不留兼容层，不写兜底。**
   - 旧运行保留在磁盘上可读，但不续跑、不迁移；
   - 不保留旧格式分支、旧阶段别名和 legacy 导出；
   - 契约只在边界校验一次，内部不重复检查，不为假想错误写兜底路径。
3. **一个共享研究状态。** 主张、证据、运行、草稿是同一张图，论文是它的视图。
4. **证据门控。** 科学结论只由证据决定，不由讨论票数决定。
5. **生成性讨论放开，评判性讨论交给证据。**
   - 专家之间可以自由提出、延伸、组合、反驳想法；
   - “有没有效”由实验回答；
   - “能否有效检验”由批评者依据有效性规则和资源判断。
6. **先独立，后交流。** 保护提案的多样性。
7. **三层嵌套循环，每层可回退。** 方向、idea、实现三层，后续环节的否定性证据都能把主张退回作者修订。
8. **专家贯穿全程。** 同一位专家负责提出、诊断、撰写、反驳。
9. **统一控制原语。** 每一步都是“产出者 + 批评者 + 有上限循环”。协调器只管状态、预算、回执，不做科学裁决。
10. **资源决定规模，不决定价值。**
    - 评测底座、筛选数量由声明的资源推出；
    - 超出资源的方案标为“当前资源无法验证”，保留其研究价值和所需资源说明；
    - 预算耗尽记为“预算内未完成”，不等同于实现失败或机制失败。
11. **简洁而非限额。** 控制代码量的目的是不写防御性兜底、不堆叠冗余结构，而不是设硬性行数上限。按模块估算规模，整体净下降；运行器、写作、底座等必要功能完整实现，不为压缩行数偷工。

## 5. 输入

项目输入只有两个文件和一个可选目录。系统流程不写进输入。

### 5.1 research.md：只写科学内容

固定五节，由 `init` 生成模板：

1. **问题与范围**：研究问题、示例、不研究什么。
2. **任务定义与指标**：形式化定义、主要指标、工作点、统计要求。
3. **评价有效性规则**：数据构造、划分、泄漏、可比性等必须满足的条件。底座审查逐条核对。
4. **开放问题**：需要实验回答的问题。领域全景按这些问题组织，选队和提案都不得预设答案。
5. **非约束性线索**：文献、数据、代码入口，固定标注“仅供调研，不代表优先级或技术路线”。

研究闭环、预期交付等流程描述删除，由系统定义；资源与运行安排移入 toml。

### 5.2 paperagents.toml：结构化配置，由程序读取

| 节 | 字段 | 用途 |
| --- | --- | --- |
| `[resources]` | `device`、`memory_gb`、`gpu`、`wall_clock_days`、`api_budget` | 底座规模、可验证性判断、预算分配 |
| `[data]` | `allowed_sources`、`download`、`license_notes` | 数据获取与构造的边界 |
| `[loops]` | `screen_top_n`、`exploratory_slots`、`evolve_rounds`、`target_good`、`engineering_budget`、`seeds`、`max_candidates_per_expert` | 中层与内层预算 |
| `[output]` | `venue`、`template`、`page_limit`、`anonymous` | 写作通道 |
| `[checkpoints]` | `testbed`、`final_method`、`submission` | 人工检查点；为 true 时暂停等待确认 |
| `[research]` | `lookback_years`、`core_papers`、`allow_temporary_experts` | 保留 |
| `[glm]`、`[execution]` | — | 保留 |

删除 `[discussion]` 节，以及 backend 中的 `command`。

### 5.3 inputs/（可选）

存放用户已有的数据、代码、权重、论文。知识准备和底座构建阶段优先使用；协调器记录哈希，作为证据来源。

### 5.4 cir-reliability 的迁移

- 按 5.1 重组 research.md；
- 资源写入 `[resources]`：M4、16 GB、无 GPU、本机执行；
- i-CIR、CIRR 移入“非约束性线索”，其使用约束保留在有效性规则中；
- 新建运行，不续跑旧运行。

## 6. 角色

按职能设四类角色，每类可有多个实例；不按阶段拆分 agent。

| 角色 | 实例 | 职责 | 独立性规则 |
| --- | --- | --- | --- |
| 专家 | 领域专家、论文（方法）专家、临时专家 | 知识、提案、交叉意见、失败解释、撰写章节、反驳论证。领域专家另兼：讨论引导者（指出领域全景中无人提案的开放问题，不裁决）、主编（叙事与 LaTeX 统稿） | 不判定自己的主张 |
| 工程师 | 按任务派生 | 获取与构造数据、实现方法、调试、执行消融与补充实验 | 不提交分数，分数只由运行器产生；不修改主张 |
| 批评者 | 按判定派生，与作者隔离 | 协议有效性、idea 的可检验性与资源可验证性、六维评估、运行判定、代码与方法一致性、查新 | 只判定，不写方法和代码 |
| 评审团 | 多位审稿人 + meta-review | 论文评审，决定定稿、退回或降级 | 不参与写作 |

**由协调器程序完成、不用 agent 的部分**：分数计算、数字宏生成、引用来源核对、LaTeX 编译、预算与进度推进。

**现有角色的去向**：

- `researcher` 拆入专家（知识任务）与工程师（数据和实现）；
- `verifier` 扩展为批评者；
- 主持人与综合者删除。去重由批评者初筛加作者确认完成；主方法定稿由领域专家依据证据提出，再经批评者核对。

## 7. 共享研究状态

每次运行一个 `state/` 目录，协调器是唯一写入者。共四类对象：

| 对象 | 关键字段 | 说明 |
| --- | --- | --- |
| Claim 主张 | `claim_id`、`version`、`kind`、`text`、`owner`、`parents`、`verdict`、`stage`、`evidence_ids` | 论文中可检验的陈述都来自主张；任何科学内容的修改都生成新版本 |
| Evidence 证据 | `evidence_id`、`kind`（literature / run / diagnosis / assessment / review）、`claim_ref`（`claim_id@version`）、`source`、`hash` | 证据绑定到具体主张版本 |
| Run 运行 | `run_id`、`claim_ref`、`protocol_id`、代码清单哈希、`split`、`seed`、`metrics`、`outcome` | 不另设实现对象，实现由代码哈希表示 |
| Draft 草稿 | LaTeX 章节；段落标注 `claim_ref`；数字为由证据生成的宏 | 不手抄数字 |

**两个独立字段，不混用：**

- `verdict`（科学结论）：`untested`、`supported`、`refuted`、`inconclusive`、`unverifiable_with_resources`。只由证据改变。
- `stage`（工作进度）：`proposed`、`exchanged`、`screening`、`confirming`、`novelty`、`ablation`、`frozen`、`tested`、`written`。由流程推进。

**运行结果 `outcome`**：`completed`、`impl_failed`、`protocol_failed`、`budget_exhausted`。批评者依据与主张相匹配的有效证据判断 `verdict`：完成且协议有效的运行才可作为效果证据；运行完成不代表支持或反驳，样本不足或结果不明确记为 `inconclusive`。文献可支持或反驳文献性主张；诊断、评分和评审本身不能证实效果。资源评估可标记 `unverifiable_with_resources`。其他运行结果记为工程或资源事实。

被反驳的主张不删除，保留为负面结果或局限。现有的候选谱系、哈希回执、阅读锚点并入这张图。

## 8. 三层循环

### 8.1 外层：方向（天）

- **K1 知识准备**：scope → corpus → reading → domain → selection → expert。
  - reading 产出论文卡与覆盖记录；深读只对入选的核心论文，在 expert 阶段进行；
  - 领域全景按开放问题组织，选队先比较竞争路线与团队组合（均已实现）。
- **K2 评测底座**（专家设计，工程师执行）：
  - 按 `[resources]` 与 `[data]` 确定规模；
  - 数据划分为开发子集、开发全集、封存测试三份；
  - 定义指标与种子数，复现强基线；
  - 记录可观测的失败现象、有证据支持的归因、竞争解释和尚未区分的部分；召回、感知、联合判断、接受决策仅是 CIR 的示例，允许原因重叠和未知，不要求先得到各自的失败比例；
  - 开发子集要能在资源预算内支撑一批 idea 的筛选。
- **K3 协议审查**（批评者）：逐条核对 research.md 的有效性规则，包括标签、泄漏、划分独立性、统计前提。
  - 审过的公共协议记为 `protocol_id`，可被后续运行复用；
  - 新方法引入新的数据处理、标签使用或评价方式时，对变化部分再审；
  - 不通过则回到 K2；问题框定被证据推翻则回到 K1。

### 8.2 中层：idea（小时）

1. **I1 独立提案**：专家依据领域全景、实测诊断与自身方法知识密封提案，标注 `kind`。
2. **I2 交流**：见第 9 节。所有专家阅读全部提案并给出交叉意见，作者修订一次。
3. **I3 去重**：批评者初筛归组，作者确认合并、撤回或说明差异（已实现的 triage / merge）。
4. **I4 可检验性评估**（批评者）：
   - 判断能否有效检验、当前资源能否验证；
   - 给出六维评估（第 11 节）；
   - 无法有效检验的退回作者，资源无法验证的标为 `unverifiable_with_resources` 并保留。
5. **I5 组合选拔**：选出进入筛选的一批，覆盖不同开放问题和 `kind`，并含 `exploratory_slots` 个探索名额；不只取最有把握的几个。
6. **I6 子集筛选**：工程师实现，运行器执行，批评者判定。
   - **有希望**：进入确认阶段；
   - **无效**：`verdict=refuted`；
   - **待工程**：进入内层，预算用完记为 `budget_exhausted`。
7. **I7 解释**：提出者解释结果，其他专家可补充竞争解释。解释相互冲突时，设计判别实验。
8. **I8 修订与进化**：专家依据全部成败证据修订自己的候选，或通过交流生成组合与新候选，回到 I4。满 `evolve_rounds` 轮或得到 `target_good` 个通过确认的主张时停止；全部失败且解释指向问题框定时，回到外层。
9. **I9 全集确认**：用新种子在开发全集上验证，用于抵消子集筛选中的“赢家诅咒”。失败则退回 I8 修订。
10. **I10 查新**：只对确认通过的主张做深度查新。发现撞车时退回 I8，由作者收窄、修改或撤回。
11. **I11 消融**：逐组件归因并删除无效组件。若消融否定了核心机制，退回 I8；若只删减组件，生成新版本，重新在开发全集上确认。

**每个阶段的“通过”只代表获得继续验证的资格，不是终点。** 全集确认、查新、消融的否定性结果都通向作者修订或主张降级。

### 8.3 内层：实现（分钟）

工程师实现 → 运行器执行 → 工程师调试，以 `engineering_budget` 为上限。批评者核对代码与对应主张版本是否一致。

## 9. 讨论机制

**生成性讨论**（放开）：

- **I2 交流**：每位专家阅读全部提案后，可以做四件事：
  - 延伸：在他人提案上加入自己的机制；
  - 组合：跨论文迁移，组合成新方案；
  - 反提案：对同一现象提出竞争解释及方法；
  - 指出问题：写明理由与可检验的影响。
- **作者回应**：作者阅读针对自己提案的交叉意见，修订一次（保留谱系），或说明不采纳的理由。只有一轮，不设多轮辩论。
- **探索名额**：每位专家可提一个不受实测诊断约束的高风险想法，标为探索性。
- **引导者**：领域专家指出领域全景中哪些开放问题还没有提案，不裁决。
- **实验后**：I7 的解释和 I8 的进化同样开放给所有专家，他人的失败可以成为自己的线索。
- **数量上限**：`max_candidates_per_expert` 只限制每位专家最终进入 I4 的数量，不限制交流内容。

**评判性讨论**（交给证据）：

- 效果是否成立：由运行回答；
- 能否有效检验、资源能否验证：由批评者回答；
- 解释冲突：转为判别实验。

## 10. 写作与评审通道

| 步骤 | 时机 | 内容 |
| --- | --- | --- |
| W0 骨架 | K3 通过后 | 会议 LaTeX 模板；问题、相关工作（来自领域全景与语料 bib）、实验设置 |
| W1 增量更新 | 主张版本或结论变化时 | 负责专家改写对应段落；数字宏只引用开发集证据 |
| W2 开发集初稿 | 中层停止后 | 基于开发集结果写完整初稿，包括方法、分析、局限（含被反驳的主张） |
| W3 评审 | 初稿后 | 评审团评审并给出六维评分。意见分为三类：写作修改；补充实验（只用开发集，回到中层）；主张降级 |
| W4 meta-review | 评审处理后 | 达标进入 W5；否则退回中层，或降级主张后重新评审 |
| W5 冻结 | meta-review 通过后 | 冻结方法版本、协议与要报告的主张清单（预注册）；`[checkpoints].final_method` 为 true 时等待确认 |
| W6 最终测试 | 冻结后 | 封存测试只评一次，生成最终结果宏与表图 |
| W7 定稿 | 最终测试后 | 用测试结果更新结果段落。此后只允许修改文字或降级主张，不能修改方法；若测试结果推翻主张，如实报告 |
| W8 编译与核对 | 定稿前 | LaTeX 编译；引用来自语料 bib；每个数字都可追溯；匿名化；`[checkpoints].submission` |

## 11. 评分与可追踪性

**六维评分迁移，不删除。** 六个维度沿用现有定义：问题价值、新颖性、机制合理性、证据质量、实验可判别性、可行性。

- I4 中批评者对每个候选版本给出六维评估，作为 `assessment` 证据绑定到该版本；
- W3 评审团对论文使用同一套维度。

评分只描述状态，不聚合为总分，不替代运行结果，也不单独决定晋级。

**网页全过程追踪保留并扩展：**

- 现有的对话池、任务、错误、专家、领域图谱、时间线保留；
- 对话池纳入交流、作者回应、实验后解释与进化；
- 新增四个视图：主张（版本、结论、进度、谱系）、证据（来源与绑定版本）、运行（结果、日志、代码哈希）、草稿（章节与引用的主张）。

## 15. 实施：按可运行版本推进

每个版本都是完整可运行的闭环：同一提交内新模块上线、被替代的模块删除，完成本地工程验证后自动提交并推送 GitHub，不再单独确认；研究运行和真实实验验收由用户操作，后续修复形成新提交。

### V1：提案、交流、实验、解释、修订闭环

- **范围**：
  - 新输入结构（5 节）；
  - 四类角色；
  - `state.py`；
  - 最小运行器；
  - 最小有效评测底座：开发子集、支撑实际指标的数据构造与强基线复现；计算 FAR₀ 前必须具备来源可核验的无解查询；公共协议审后复用，变化部分再审；
  - I1–I8（提案、交流、去重、可检验性与六维评估、组合选拔、子集筛选、解释、修订与进化）；
  - 网页的主张与运行视图。
- **同提交删除**：第 4 节中标为 V1 的全部内容。
- **验收**：工程夹具先验证一轮“修订后再筛选”，不冒充 CIR 科学结果；真实 cir-reliability 验收由用户执行。V1 按限定轮数结束，暂不使用依赖 I9 的 target_good 条件；V2 接入确认后启用。网页可追踪主张的版本、证据和运行。

### V2：完整验证链

- **范围**：
  - 完整评测底座与协议审查（含无解查询构造）；
  - I9–I11（全集确认、查新、消融）及其回退路径；
  - 增量补检索；
  - 证据视图。
- **验收**：存在一条从筛选到消融的完整主张链；任一否定性结果都能退回作者修订。

### V3：写作与评审

- **范围**：W0–W8、评审团与 meta-review、补充实验回流、冻结与最终测试、草稿视图、API 预算。
- **验收**：产出可编译的会议 LaTeX 论文，每个数字可追溯，最终测试只执行一次。

## 16. 待确认事项

以下内容写入新的输入文件，V1 迁移时需要你确认：

- **算力**：目前为 M4、16 GB、无 GPU、本机执行。在这一条件下，评测底座以冻结特征加轻量方法为主；需要训练大模型的方案标为“当前资源无法验证”。是否准备 GPU，决定 `screen_top_n` 等规模参数。
- **数据**：无解查询与部分匹配负例的构造方法、允许的数据来源与许可、可接受的人工标注量。
- **会议**：首个目标会议与模板、页数、是否匿名。
- **人工检查点**：建议三处——底座协议、主方法冻结、投稿前终稿。

## 17. 风险

- **重写范围大**：按 V1–V3 推进，每版可运行、可验收。
- **子集误杀与开发集过拟合**：确认阶段用新种子在全集上验证；最终测试封存且只评一次。
- **评审过拟合**：评分不作为唯一信号，关键结论以证据和人工检查点为准。
- **本机算力**：限制方法类型与筛选规模；结论的适用范围在论文中如实说明。
