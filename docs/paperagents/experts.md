# 专家与技能设计

PaperAgents 的专家应是带来源、实现和验证记录的知识包。当前新增技能定义了从领域学习到提案审查的研究行为；它们不会仅靠提示词创建科学有效性保证。实际阶段与产物格式以 [artifacts.md](artifacts.md) 和任务提供的 schema 为准。

## 先学习领域，再建立核心团队

1. 明确研究问题或任务、近三年的具体日期窗口、目标会议集合和纳入标准；枚举会议目录，交叉检索关键词、机制和引文。
2. 学习纳入论文的正文与补充材料，记录全文缺失、版本差异、失败与矛盾；形成逐篇研究论证轨迹和覆盖报告。
3. 建立领域专家，组织问题地图、机制谱系、评估条件、研究路线、已知分歧和机会。
4. 在领域知识基础上选择三篇互补的核心论文，再分别构建论文专家及方法工具，并独立核验。

常驻团队是领域专家加三名论文专家。三篇限制团队规模，不限制语料规模；领域专家仍应能访问整个已学习语料。选择依据包括相关性、机制互补、论证/证据质量和研究问题，不以引用量或会议声望直接排序。

当某项推理依赖领域外机制、统计能力、数据协议、实现细节或新论文时，创建有明确任务边界的临时专家。临时专家需注明来源及材料缺口；缺材料不能靠角色命名补齐。完成任务后把核验后的知识交回领域知识库，保留来源与版本。

## 学习研究思路，而不编造作者心理

每篇论文记录问题/观察、已有局限、假设、设计选择、预测、实验与反证、结论和边界。知识中区分四种来源：

| 分类 | 允许表达 | 证据要求 |
| --- | --- | --- |
| 原文事实 `source_fact` | 原论文或代码直接报告了什么 | 精确来源、版本及锚点；作者报告与本系统观测分开 |
| 作者明确思路 `author_reasoning` | 作者明确说为什么这样做 | 对应段落、推导或作者说明 |
| 系统推断 `system_inference` | 系统如何解释或迁移机制 | 支撑来源、中间假设及竞争解释 |
| 未知 `unknown` | 原文未说、材料缺失或矛盾未解 | 已检查范围与解除未知所需证据 |

机器产物 `idea_trace.basis` 对应 `author_stated`、`reconstructed`、`unknown`。重建的是可理解的论证链，不能称为作者真实研究过程。论文组织顺序也不证明发现顺序。

详细约定见[证据规则](../../skills/references/evidence-policy.md)和[知识组织建议](../../skills/references/knowledge-layout.md)。全文学习与可追溯笔记是专家基础；单段摘要和角色描述不足以替代。

## 论文方法必须有可调用能力记录

工程技能将论文公式与方法映射到固定代码 commit，再封装输入输出、错误契约、依赖和执行入口。工具状态分层：

| 状态 | 已具备的证据 | 不代表 |
| --- | --- | --- |
| `documented` | 记录了论文到实现/接口的映射 | 已存在可运行封装 |
| `wrapped` | 有实际调用封装 | 已通过测试或结果正确 |
| `tested` | 有实际测试命令、日志和行为证据 | 已复现论文结论 |
| `reproduced` | 在明确条件下复现了指定结论 | 任意数据、规模和场景均成立 |

未运行、运行受阻、失败、部分结果或证据不足不能被成功状态遮盖。没有可执行方法的理论或分析论文仍可形成知识专家，需在 `limitations` 明确能力范围。Mock、dry run 与真实实验分开；工具目录存在不等于调度器已连接该工具。

验证规模由科学判别力决定。低成本测试可检查接口，但不能强制用弱实验替代重要结论的验证。详见[方法工具协议](../../skills/references/method-tool-protocol.md)。

## 专家贯穿构思、实验与写作

| 阶段 | 领域专家 | 论文专家 | 临时能力 |
| --- | --- | --- | --- |
| 构思 | 判断问题价值、比较路线与证据 | 提出和质疑具体机制、解释迁移条件 | 补齐外部机制、理论或数据知识 |
| 实验 | 判断结果在领域内的含义、比较竞争解释 | 核对原方法与实现、诊断异常、修订假设 | 统计、工程、资源与专项评估 |
| 写作与审查 | 核对研究定位和论证边界 | 核对方法归属、原文事实与证据支持 | 独立证据审查、专项检查 |

这些职责描述知识的复用方式。当前 `native_expert_loop` 已具备将一次真实搜索实验结果回传到专家 `hypothesis` 修订的执行路径；写作阶段自动回调专家尚未接入当前主链。运行入口为 `paperagents research/experiment --execute`，不经过原 v3 的 `create-idea`，详见[运行流程](runtime.md)。

新运行（v3）中，专家先独立输出机制卡，经重叠初筛和领域专家议程后进入讨论循环：编号异议、作者逐条答辩、原质疑者独立复核，必要时多轮，再做查新、综合和独立复核；详见[讨论循环](ideation-discussion.md)。共同事实可共享，未提交观点不预先共享。历史 v2 运行仍是一轮交叉挑战，不自动派发作者答辩。需要修订时由协调器显式退回相关阶段，提供异议及版本；不能编造未发生的作者回复、修复或共识。角色数量、投票、Elo、审稿分和一致意见都不构成科学证据。

调度器按固定阶段推进，讨论轮次由异议台账决定，不是自由对话池。领域专家负责选论文、列出讨论议题和综合；议程只决定讨论什么、由谁回应，任务派发和状态推进仍由程序控制。实验工程 worker 负责实现获批机制，独立实验评审负责检查实现与协议；这两个执行角色不能绕过核心专家另起一个未经审查的 idea。

原生链路先 `experiment_build`，再 `experiment_review`，审查通过且显式执行后，用同一冻结评价器、数据和协议评估基线与候选。协调器将实际指标、失败、代码版本及判读规则登记为 `search` 反馈，再调用 `revise("hypothesis", ...)` 触发下一轮专家判断。运行失败、结果不充分和假设被反驳须区分；专家的任务是解释真实证据并调整判断，不是让六维分数持续上升。默认不加 `--execute` 时只进行构建和审查，不运行这组实验。

## 可核验的晋级

当前专家验收是知识资产审查：验证者从原始材料独立抽查，并检查知识包里的来源区分、公式/机制解释、边界、未知、实现定位及已有修订依据。程序尚未单独向被审查专家派发验收题，因此通过不能解释为实际答题或迁移能力已测得。可设计后续测评题，但只有真实回答记录才可用于能力判定，不能让验证者代答后自判通过。

提案综合结果可以是 `ready`、`needs_evidence` 或 `no_viable_idea`；`ready` 只表示可以交给实验阶段，并仍需独立提案审查。新增机制、改变核心假设或关键前提、组合产生新交互时，当前综合任务必须返回 `needs_evidence`，安排新候选的挑战与查新；不能沿用原候选的 ID 和通过结论直接放行。关键异议、全文缺失、不可判别的实验或未核清的重叠不能因为流程预算耗尽而自动放行。

结构校验能检查必填字段、来源列表和状态一致性，不能保证引用真实、全文确已学习、代码正确或结论成立。这些需要实际工具检查、独立审查和实证。系统检索应报告明确范围及遗漏，不承诺“找齐全球全部相关文献”。

## 项目内加载与维护

21 项技能按 `knowledge`、`engineering`、`ideation`、`review` 组织，入口见 [skills/README.md](../../skills/README.md)，主程序按 [registry.json](../../skills/registry.json) 的 ID 加载，无需全局安装。`paper` 默认预载五项：`build-paper-expert`、`understand-paper`、`trace-paper-ideas`、`distill-reasoning-patterns`、`map-paper-code`；通过 `execution.paper_capabilities` 按需加入 `communication` 或 `method_tools`，分别增加表达学习或方法封装／验证。写作与图表表达合为一项学习能力；有旧资产才加载复用检查，有真实旧候选才加载修订。论文理解、论证图和可迁移策略的细化与 v2 契约见[三层能力](paper-expert-capabilities.md)。

专家知识、来源版本、工具版本与运行记录分别持久化。新文献、代码变更或矛盾结果触发受影响部分更新及重验；保留旧知识与候选谱系，保证已完成研究能够按当时证据重建。

当前复用是本项目内按专家身份寻找历史版本，再检查范围和来源；没有自动跨项目语义检索。知识包和工具清单也不是自动部署的 MCP 服务：只有已实现且在对应环境验证过的接口，才能声称具备可调用能力。

目前尚未用用户提供的真实问题 Markdown 完成模型驱动的科研试跑。上述能力边界来自实现和框架检查；专家是否能稳定提出更好的 idea，仍需真实文献核查、实验结果及独立对照评估。
