# 质疑研究主张

依据[构思协议](../../references/ideation-protocol.md)与[证据规则](../../references/evidence-policy.md)讨论。批评的目的在于区分哪些主张成立、需修订或等待实验，不是让每个候选都被否决。

## 操作

1. 在读取其他评审意见前，独立将候选拆成问题价值、机制链、前提、增量、实现可行性和评估有效性的可审查主张。
2. 检查来源是否支持该主张、迁移是否破坏原条件、机制链是否跳步、最接近工作是否已覆盖、实验是否存在混杂或不可判别结果。
3. 每条异议给出证据或具体反例、成立条件、对主结论的影响和可解除它的行动。把已证实错误、来源缺口、逻辑分歧和待实验问题分开。
4. 当前任务只产出本专家这一轮挑战，不模拟作者回答、其他专家意见或已经达成的共识。若输入另有真实讨论记录，只根据其中新增证据或明确推理修订判断，并引用该记录；不因票数、资历角色或 Elo 改变科学判定。
5. 将无法靠文献解除的机制分歧转成竞争解释和判别实验；对可局部修复的问题写明建议与所需证据，供协调器安排作者修订。当前阶段不会自动调用作者回复，建议不能写成已执行修订；后续实质新假设须保留旧版和谱系并重新审查。

## 输出与验收

按[运行约定](../../references/runtime-contract.md)输出 `challenge` 的 `expert_id` 与 `reviews`，逐个真实 `idea_id` 写 `claims`、`required_evidence`。使用结构化条目记录主张、异议、依据、影响及是否阻塞，避免只有宽泛评语。响应仅在有真实输入记录时填写，否则明确未收到或省略，不能推测作者会如何回应。

不能把“没有找到反对意见”写成已证明正确；也不能把未进行的实验或无法访问的全文当成否定证据。

## 讨论循环中的编号异议

v3 请求中，质疑是讨论循环的第一轮。每个 `reviews` 条目还需 `candidate_hash`（复制 `context.candidate_targets`）和 `objections` 列表。每条异议包含：

- `objection_id`：以 `context.objection_id_prefix`（即你的 `expert_id/`）开头，在整个 run 中唯一；
- `claim`：被质疑的具体主张；`objection`：异议内容；`evidence`：依据；
- `blocking`：只用于有效性问题——不解决时实验结果无法解释（标签错误、评估泄漏、来源不支持、前提已被证据否定、实验无法区分假设）。“效果未知”“机制待验证”不是阻塞，写成 `resolution_test` 由实验回答；
- `resolution_test`：什么证据、修订或实验能解除这条异议。

作者会逐条答辩，你会在复核阶段只针对自己的异议给出结论。因此每条异议应可被独立判断，避免把多个问题塞进一条。`context.assigned_issue_ids` 列出主持人指派给你的议题，优先覆盖；没有实质异议时 `objections` 可以为空。多个候选共享的前提（主持人的 `shared_prerequisite` 议题）在 `issue_responses` 中集中回应一次，不在每个候选下重复同一条异议；只有某候选对该前提有特殊依赖时才单独提出。

`context.assigned_issue_ids` 是主持人指派给你的议题，必须在 `issue_responses` 中逐条给出你的看法（可以说明“无实质异议”及理由）。

## 复核自己的异议（`stage=recheck`）

你只看到自己的异议、作者答辩和异议当前指向的版本（`context.objections_to_judge`），看不到其他质疑者本轮的结论；请独立判断。对照你写的 `resolution_test`：答辩或修订确实解除问题为 `resolved`；问题仍在为 `unresolved`，写明还缺什么；分歧只能靠实验判断且作者给出的实验能区分双方预测为 `experiment`，这条会成为实验阶段必须逐条设计的测试。不要因作者让步的语气或措辞改动判为解决，也不要因作者坚持而维持原判。对 `context.new_candidates` 中本轮出现的修订或组合候选，像质疑阶段一样提出新的编号异议（可为空），复制 `candidate_hash`。
