# 构建领域专家

专家的能力来自可追溯知识和验证记录，不来自角色身份措辞。先读[专家生命周期](../../references/expert-lifecycle.md)与[证据规则](../../references/evidence-policy.md)。

## 输入

使用当前版本的方向范围、全文语料、覆盖报告、逐篇研究轨迹及已知缺口。若领域构建仅提供三篇论文或若干摘要，不能把结果声明为已完成领域学习；先记录不足并请求调度器补充语料。

当 `stage=consultant` 时，只围绕任务明确的 `specialty` 构建临时能力，按材料核验专题知识及适用条件，不声称已经学习整个领域。没有材料时记录缺口与限制，不靠专家角色名推定具备能力。

## 从领域图谱出发

协调器已把逐篇阅读的论文卡合并为 `context.domain_graph`：`index.md` 列出问题及论文数，`problems/` 按问题分文件，`graph.json` 含问题、方法、结果和论文间关系。索引每行是一篇（或同问题的几篇）论文及其方法，先通读索引掌握全部语料，再按问题打开 `problems/` 文件，必要时回到单篇阅读记录或全文；不要一次装入全部材料。

领域专家的核心产物是 `knowledge.landscape`，所有 `paper_ids` 必须是已有阅读记录的论文，程序会校验：

- `questions`：按 research.md 的开放问题组织（例如瓶颈问题要分别覆盖召回、细粒度感知、联合条件判断、接受决策）。每项写 `paper_ids`（与该问题相关的已有方法与证据）、`known`（已有方法和证据说明了什么）、`unknowns`（尚未回答的部分）、`observations`（哪些观测或实验能区分竞争解释）、`corpus_gaps`（语料里缺的来源类型，如“没有用视觉语言模型做候选验证的论文”）。不要在实验前替问题下结论：“目前无法确定，需要这些观测”是合格答案；也不要求每个问题都有创新空白。保留竞争解释，不把全景收窄到某一个方向。
- `set_aside`：与所有问题都无关的论文及理由。每篇已有阅读记录（complete 或 partial）的论文必须出现在某个问题的 `paper_ids` 或 `set_aside` 中，程序会校验，以防整类方法被静默忽略。归入问题意味着你读过它的论文卡并能说明它与该问题的关系，不是为凑覆盖而填写。
- 区分“已有论文没被综合”和“确实没有相关来源”：前者在本阶段补读并纳入，后者写进 `corpus_gaps`，由调度器决定是否补检索。

- `evolution_chains`：参照 Chain-of-Ideas，按时间或依赖顺序列出论文链（至少两篇），`steps` 写每一步改变了什么假设或机制；
- `contested`：有正反两方论文支持的争议主张；
- `gaps`：`问题 × 条件或方法` 的空白，状态为 `untested`（没人试过）、`failed`（试过且失败）、`inconclusive`（证据不足）；后两者必须给出证据论文；
- `protocols`：主流评估协议及其盲点。

这些视图服务后续阶段：`questions` 是选队覆盖表的依据，空白引导提案，争议进入议程，失败记录用于质疑，协议盲点用于实验设计。

## 操作

若任务提供 `context.reuse_candidates`，先用 [reuse-and-update-expert](../reuse-and-update-expert/SKILL.md) 核对旧专家的范围、语料时间窗与来源版本，记录可保留内容和本次增量；旧覆盖结论不能替代当前语料检索。

1. 组织任务与问题地图：主流假设、评价目标、关键数据、基线、约束与尚未解决的矛盾。明确领域采用的评估协议及其潜在盲点。
2. 归纳机制谱系与研究演进，比较哪些论文沿用、反驳或改变了哪些假设。每条跨论文结论保留支持与反对证据。
3. 建立可迁移机制与边界库：何种条件下生效、何种条件下失效、哪些结果尚不足以解释原因。将系统推导和原文结论分开。
   使用 [distill-reasoning-patterns](../distill-reasoning-patterns/SKILL.md) 按具体思维操作组织跨论文策略：对比输入问题、被修改的假设、保留的关系、操作结果及失败条件；同一策略标签下的机制不同就分别保存。每次归纳回链到论文与轨迹，不把多篇论文重复引用视为独立验证，也不因缺乏可迁移策略而编造一条。
4. 形成研究机会清单，说明问题重要性、已有最接近解法、未解决的证据缺口与可判别预测。不要立即替整个团队决定唯一 idea。
5. 建立按主题检索的知识入口，链接完整笔记、来源和工具。记录当前版本、知识覆盖、能力不足、维护触发条件及待验证问题。

## 输出与验收

输出当前 `domain` 或 `consultant` 任务 schema 的 `knowledge`，遵循[运行约定](../../references/runtime-contract.md)，按需使用[知识组织建议](../../references/knowledge-layout.md)。保留 `source_fact`、`author_reasoning`、`system_inference`、`unknown` 四类条目与引用。

领域专家应能解释整个已学习语料的结构，并为三篇专家选择提供比较依据。临时专家写明其进入团队原因、材料来源及交接边界。知识包交由 [verify-expert](../verify-expert/SKILL.md) 检查；未经验证不自行声称“已精通”。
