# 专家生命周期与复用

## 常驻团队与临时能力

常驻团队由一名领域专家和 `context.core_papers` 名论文专家组成（默认三名）。领域专家由系统语料学习构建，负责研究地图、问题价值、证据分歧和跨论文关联；论文专家负责某篇论文的完整论证、假设、实现和失败边界。核心论文的选择发生在领域学习之后，按与目标相关性、机制互补、证据质量及可研究的问题选拔，不按引用量排名凑数。

配置允许时，临时专家由具体知识缺口触发，例如统计设计、数据泄漏、某个外部机制、系统性能、代码实现或新出现的相关论文。记录任务、输入证据、能力边界和输出；结论经核验后进入共享证据库，角色可以退出。不得让无限增加的角色替代补材料或做实验。

## 可复用专家包

专家包是版本化知识与能力记录，不是声称自己“世界顶级专家”的提示词。至少包含：身份与范围、来源清单和版本、研究地图/论文论证轨迹、带来源类型的主张、适用与失效条件、反证和未决问题、可调用工具索引、验证记录、维护记录。

入口保持简短，详细论文笔记、公式、图表、实现映射和日志按需加载。压缩摘要不能丢掉支撑锚点与条件，也不能替代对正文及补充材料的学习。不同运行可以复用相同知识版本；一次讨论产生的新推断必须单独记录，不得自动污染基线知识。

领域/论文构建时，调度器按专家 ID 提供项目内旧资产候选；有候选就按[复用协议](expert-reuse-protocol.md)核对来源、范围、时效和能力证据，再决定保留、增量更新或重建。知识复用、工具可调用与结果可复现分别判断。匹配由 worker 执行，仍需当前独立审查，不是跨项目自动缓存或跳阶段机制。

## 参与构思、实验、写作

- 构思：用自己的机制与证据提出独立假设，指出对方方案可能违背的前提，标注迁移步骤。论文专家不必始终维护自己的论文。
- 实验：解释原方法实现与评估条件，检查改动的因果含义，诊断异常，设计能区分竞争解释的实验。
- 写作与审查：核对相关工作、方法归属、证据支持程度和主张边界；作者式流畅措辞不能扩大结果。

领域知识可以共享；尚未提交的初始观点不共享。新运行的构思流程是独立候选、初筛、领域专家议程、编号异议、作者答辩与原质疑者复核（可多轮）、查新与综合；复核时质疑者只看到自己的异议与作者答辩，其他质疑者的判断在本轮结束后才公开（历史 v2 运行为一轮交叉挑战）。保存少数意见及未解分歧；多个 agent 同意同一未经核验的主张不会增加证据强度。需要作者修订时，由协调器显式退回相应阶段，不把下一轮尚未发生的讨论写成历史。

## 验证与更新

当前 `expert_review` 验收知识资产：验证者独立抽查原文片段，检查包中的公式和设计解释、来源与推断区分、不适用条件、未知、代码定位及修订依据。记录实际核对的资产条目、来源、判定理由和失败项，不能只留一个模型打分。

真实能力测评还需要给被审查专家派发问题并保存其实际回答；当前调度器没有这一步。可以提出题目和有来源的期待条件作为后续测评计划，不得将验证者自己写的答案当作被审查专家的表现。只有实际提供答题记录时才评价该回答，并关联问题、知识版本、来源与判定理由。资产审查通过不等于交互能力已测得。

知识验证、工具验证、结果复现分别报告。没有运行条件时可完成静态知识检查，仍必须明确工具未运行及复现未知。影响核心能力的失败要求修订后重验；普通补充材料缺口保留可见限制，不能用全局 `pass` 隐藏。

来源版本改变、代码 SHA 改变、出现矛盾结果或发生数据/评估协议变化时，检查受影响条目并生成新版本。保留旧版本供已执行研究重建。
