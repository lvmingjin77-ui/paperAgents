# 候选修订、回应与谱系

## 何时使用

用于已提交候选收到真实挑战、最近邻比较、实现反馈或可使用的搜索实验结果之后。初次独立生成候选仍使用 [generate-hypotheses](../ideation/generate-hypotheses/SKILL.md)，不得为了填写回应表预先想象其他专家的批评。

执行修订前应能定位：父候选的 `idea_id` 与不可变产物、知识/来源版本、每条待处理异议的实际条目、已有查新范围和实际反馈。显式退回后的 `context.revision_context` 提供 `previous_iteration`、`reason`、`previous_hypotheses`、`challenges`、`novelty`；检查其中的 `task_id`、`artifact_path`、`artifact_hash` 回执与数据。只处理当前专家自己的旧候选，不将过滤后未出现的其他专家意见推定为赞成。缺少输入就明确记录缺口；修订原因的一句概述不能替代原始候选和证据。

`previous_hypotheses` 各项的 `data` 含原 `expert_id` 与 `candidates`；`challenges` 各项含评审者 `expert_id` 及过滤后的 `reviews`，`novelty` 各项含过滤后的 `reviews`。回执哈希对应完整历史产物，不能拿过滤后的片段计算哈希再误报来源不一致。以已提供的相关条目为修订范围，不借回执路径扩展阅读无关候选或把缺失条目当成支持证据。

## 对每条异议作出可追溯回应

引用实际挑战产物及条目位置，先准确复述被质疑的主张，再区分：

| 情形 | 应作判断或行动 |
| --- | --- |
| 事实或来源错误 | 核对原文并纠正；若影响机制或前提，产生后代候选 |
| 推理跳步或条件不成立 | 补足有依据的推导、收窄适用范围，或撤回该主张 |
| 最近邻已覆盖 | 比较具体机制与边界；没有实质差异就撤回创新主张，不靠改名规避 |
| 实现受阻或接口错误 | 区分工程问题与科学反证；说明是否影响原假设的可检验性 |
| 多个机制均能解释观测 | 保留竞争解释，设计区分预测；讨论不能代替实验 |
| 异议本身缺乏依据 | 给出可核对的反证或解释；证据不足时保留分歧，不虚构对方认可 |

每条回应说明所用证据、保留或改变了什么、剩余不确定性以及下一步。采纳某条意见必须能指出它改变判断的理由；多数赞成、专家资历或审稿分不能充当理由。

## 保留、修改、撤回、合并

- **保留**：现有主张及其条件仍值得检验。回应异议并保留尚未证实的状态；没有新证据不等于异议已解除。
- **修改**：给出改前/改后差异、理由及受影响的预测、来源和评估。修改候选机制卡时使用新 `idea_id`，即使编辑者认为只是改善措辞，也不要改变旧 ID 下受保护字段的值；不能让旧 ID 上的通过结论覆盖新机制。
- **撤回**：停止将该候选作为当前有效方案，保存为何撤回、哪些主张被否定或仍未知、可复用的知识。没有结果与结果反驳分别记录。
- **合并**：明确每个父候选贡献的机制、新增交互、冲突条件和额外假设。使用新 ID，并重新挑战和查新；父组件的评价不能自动继承到组合。

保留父版本及旧评审，后代关系不等于另一个独立发现。新 ID 应在本次团队中唯一，并能通过父引用找回历史；不要把同一后代重复计入候选多样性。保留但未变更科学内容的候选可以沿用其 ID，仍须区分新旧产物并接受本轮所需审查。

## 准确使用实验反馈

只使用任务允许的搜索反馈。实际观测应能关联原始 `run_id`、代码版本、数据与划分、配置、日志/产物和所检验的候选版本；缺少绑定就写明它不能确定支持哪一版本。当前反馈接口记录 `evaluation_split=search`、`run_id`、`code_version`、`data_description`、`configuration`、`findings`、`artifact_refs`，不自动证明其真实性或候选对应关系。

将原始观测、解释及后代假设分开。核对原定预测后再解释支持、反驳或不能区分；报错/未执行不算机制失败，性能提升也不单独证明机制。事后新增的解释和分析必须标明探索性质，不能回写成事前预测。封存最终评估不能进入这一修订路径。

## 在现有 schema 中记录

以 `request.output_schema` 为准；下面是允许扩展时的记录建议，不是新增阶段或已由程序强制的必填 schema：

| 记录 | 建议内容 |
| --- | --- |
| `revision_log` | 每条包含父候选引用、`issue_ref`、实际回应者、`disposition`、`reason`、`evidence_refs`、`changes`、`resulting_idea_ids`、未解问题及是否阻塞；`disposition` 可为 `retain / modify / withdraw / merge / needs_evidence` |
| 候选 `lineage` | `parents` 中保存父 `idea_id`、产物路径/任务 ID 与可用版本或哈希；记录 `change_summary`、`scientific_change` 及所需重新评审；不要填虚构版本或哈希 |
| `unresolved_questions` | 在支持该字段的输出中记录具体缺口、证据取得方式、受影响主张与 `blocking: true`；它不等于问题已经解决 |

`hypothesis` 输出仍以完整机制卡为主体。所有撤回或仍需证据的旧候选都要在回应记录中有交代；不能只静默丢弃不利意见。扩展字段只是可审计说明，不会自动触发重试、停止或采纳。

## 当前调度接入边界

当前阶段没有独立的 revision 阶段。协调器显式从 `hypothesis` 退回后，后续挑战、查新、综合和提案审查会重新执行；这是已有阶段重跑，不是本技能启动了自动多轮讨论。若缺口实际在原文、知识包或专家验收，应退回对应更早阶段。

仅在 `hypothesis` 请求明确修订已有候选、并提供 `revision_context` 时按需加载完整技能；`synthesis` 使用其自身技能引用本协议作修订分流，不加载本技能去执行修订。普通初始假设任务不需要加载，只有反馈存在也不代表已安排某个候选的修订。

`Workflow.revise()` 记录退回阶段及 `reason`，清除该阶段及后续的活动 batch，并保留历史产物；修订任务通过 `revision_context` 获取当前专家自己的旧候选，以及指向这些候选的真实挑战和查新记录。首次独立构思没有这个字段。通用上下文里的 `revisions`、`search_feedback` 与候选材料需要共同核对；没有提供的历史记录不能假定已收到，更不能虚构作者答辩。协调器对已知旧 ID 的受保护字段检查一致性，不等于自动识别所有自然语言机制变化。技能不修改调度状态或原 v3 流程。

## 停止与移交

在当前指定任务内处理能由已有证据解决的问题；仍需新文献、真实实验或其他专家输入时，列明动作后移交，不在没有新增信息时重复辩论。`synthesis` 对阻塞性修订返回 `needs_evidence`；`hypothesis` 通过现有候选及回应记录说明未解决事项，由协调器决定后续动作。关键机制改变必须回到新候选的挑战与查新，不能只重做提案审查就视为原结论仍适用。
