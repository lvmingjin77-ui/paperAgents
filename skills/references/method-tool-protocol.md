# 论文方法到可调用工具

方法工具应让专家能够实际调用、测试和解释算法行为；有一段代码或一份安装说明不等于已经获得该能力。

## 映射与接口

从论文公式、算法步骤和关键实现细节映射到固定 commit 的文件/符号，注明对应程度、差异和缺失。优先检查作者提供的配置、数据预处理、训练目标、评估入口及 checkpoint 来源。区分直接调用原 API/CLI、抽取原代码适配、依据论文重新实现；最后一种需要说明未确定细节与独立正确性依据，不等于原方法封装。没有 Git 版本的源码记录文件/目录指纹，不虚构 commit。

### 可执行调用契约

以下信息应存在于工具扩展字段或随附的调用说明中；它是本技能的交付约定，不表示当前 schema 已逐字段强制校验。CLI、Python API、MCP 按实际使用方式任选；无需为几个本地函数强制创建 MCP 服务。

| 内容 | 可执行所需的信息 |
| --- | --- |
| 身份与来源 | 工具名/版本、用途与前提、实现方式、上游仓库及固定版本、文件/符号、许可、必要适配与已知偏差 |
| 调用入口 | CLI 的 argv 模板、解释器和工作目录；或 Python 模块/符号及参数；或 MCP 的启动/连接方式、工具名与调用参数。先确认入口真实存在 |
| 输入 | 类型/schema、单位与张量形状、标识符/顺序要求、参数范围和默认值、必需数据/权重及其身份。不得静默加载演示数据代替用户输入 |
| 输出与失败 | 返回 schema、产物格式/路径与语义、错误类型或退出码、无效输入行为；文件型输出说明每次调用的隔离策略与覆盖行为 |
| 运行环境 | 被测试的解释器/平台、依赖固定文件、原生库、硬件与资源、环境变量名、工作目录；不保存凭据。下载、训练和持久化副作用明确列出 |
| 随机性与组合 | 原实现实际支持的 seed、非确定性来源、工具间传递的产物/前提，不能只因接口加了 seed 就承诺可复现 |

仅拟议接口保持 `documented`。实现文件存在但未完成对应验证保持 `wrapped`。工具可调用、忠实封装、算法行为正确和目标结论复现是不同主张。

运行在项目指定的隔离环境或后端；不把本技能当成修改全局环境、提交外部任务或获取新数据授权的依据。下载、算力和数据访问沿用当前任务授权。不得把秘密、凭据或私有数据内容写入工具清单。

在 `paper`、`domain` 或 `consultant` 产物的 `source_paths: list[str]` 中列出真实 wrapper 源码、依赖说明、调用说明和已有验证记录的文件/目录，路径可为绝对路径或相对 `project_dir`。这些材料应位于稳定项目位置，不能指向临时目录、全局环境或仅留下原 host 的路径描述；调用说明应能按导出后的材料位置使用。`wrapped`、`tested`、`reproduced` 必须有可导出的 `source_paths`，纯 `documented` 可无。协调器负责内容寻址快照及 `_asset` 元数据，worker 只提交真实来源，不填 `_asset`；快照可导出不代表已通过方法验证。

## 四层证据

| 层次 | 要回答的问题 | 必需记录 |
| --- | --- | --- |
| 静态映射 | 代码是否实现了论文所述步骤？ | 来源/commit、公式与符号映射、已知差异 |
| 接口与不变量测试 | 调用是否可靠，输出是否满足必要性质？ | 实际命令、正常与错误输入、预期性质、退出状态、日志 |
| 算法行为验证 | 算法是否在可判断的输入上表现正确？ | 独立参考、解析解或受控对照、容差与失败案例 |
| 结论复现 | 是否在相同或明确可比协议下重现论文结果？ | 数据/划分/种子/预算/硬件、基线、指标实现、原始结果与不确定性 |

通过上层检查不能跳过下层；完成较低层也不能声称较高层成立。对不适用的层次解释原因。单个成功的 smoke test 只能支持该路径可运行。Mock、fixture、dry run 和模拟数据必须标明，不能支撑真实训练或真实数据复现。

### 将实际调用绑定到实际版本

验证记录至少能回答：谁在何时、哪个环境、用什么入口和输入，测试了哪些文件版本，采用什么独立预期，实际观察是什么。保存 argv/参数、工作目录、解释器与依赖指纹、数据身份、源码/测试/参考结果哈希、退出/异常状态、日志和产物位置。API 异常和 MCP 错误按实际协议记录，不杜撰进程退出码。

记录正常调用之外有判别力的改变输入/参数与错误用例；参数变化应真正影响相关结果。针对大数组、图像或复杂文件，另存科学比较结果，路径存在检查不能代替内容检查。参考调用直接使用固定的上游实现或独立论证，不从 wrapper 结果反推“预期”。失败和修复保留历史，修改源码、协议、依赖或数据后重验受影响结论，不能只刷新哈希来沿用旧通过状态。

`verification_evidence` 可引用结构化记录或真实文件，细节可放随附报告；`code_tools` 可在当前 schema 允许的扩展字段中保存 `implementation`、`invocation` 等信息。以实际 `request.output_schema` 为准，不要求增加新的顶层产物。见[精简示例](method-tool-example.md)；其中所有路径与观察均是格式示范，不能直接作为验证证据提交。

### 当前独立审查边界

`paper` assignment 请求 `method_tools` 能力时同时加载构建与验证 skill；两份指令不代表两个独立 agent。后续 `expert_review` 是独立的资产审查任务，可核查源码、版本和证据，并在实际执行条件允许时重新调用工具。审查报告应区分材料核查、构建者自测与独立复验，以及各自覆盖的范围。

论文方法工具仍没有单独强制的完整复现阶段。原生 `experiment_build/experiment_review` 构建并审查当前候选的搜索实验，随后由 Python 执行器真实运行基线和候选；这不能替代每篇源论文方法的完整复现。`tested/reproduced` 的非空引用校验与资产文件哈希检查不证明调用发生或科学结论成立。需要独立复验却缺少环境、输入或证据时，记录 `unknown` 和依赖缺口。

需要跨工作目录/机器调用时，应在新位置按说明恢复环境并通过真实入口测试；路径映射解决定位问题，不证明依赖、原生二进制或数据已恢复。只在已验证的平台和条件下声明可移植。

## 实验选择

测试规模由失败风险、算法特性和所验证的主张决定，不强制采用便宜或短时实验。有限规模的测试适合排查接口问题；如果无法辨别核心主张，必须扩大设计或把结果记作不充分。事前规定比较条件、容差、停止规则和失败解释，观察结果后变更时记录原因及其探索性质。

工具验证输出必须区分：未运行、无法运行、运行失败、检查通过、部分复现、未复现和结论不充分。具体机器枚举遵循调用方产物 schema；这些语义不可合并成一个模糊的“已验证”。
