# 构建方法工具

先读[方法工具协议](../../references/method-tool-protocol.md)和已有映射。工具目标是可调用、可解释且与所研究机制对应，不是复制整个仓库后宣称完成。

## 操作

1. 根据专家实际任务确定工具边界，绑定已核查的源码文件/符号。优先直接调用原 API、脚本或 CLI；只有缺少可调用入口时才抽取原实现，保留来源和计算语义。选择适合宿主的 Python、CLI 或 MCP 接口，不强制新增服务层。
2. 将“原实现的调用封装”“原代码抽取适配”“依据论文重新实现”分别记录。缺少原实现时先确认重新实现属于当前任务；说明公式依据、未确定细节和预期差异，不能沿用“忠实封装原代码”的验证结论。
3. 在项目指定位置和隔离环境中实现入口。按协议记录可执行调用契约：解释器/可执行文件或模块符号、工作目录、参数、输入输出结构、依赖与数据要求、失败行为、输出位置和副作用。固定上游版本、封装文件版本和依赖；只暴露原实现真正支持的种子和参数。
4. 准备来源独立的参考调用与预期，比较实际输入、默认值、单位、标识符和计算步骤。封装主要负责必要检查、调用和结果序列化；不将对照重算、演示数据加载或无来源的算法修补混入生产路径。
5. 用 [verify-method-tools](../verify-method-tools/SKILL.md) 检查真实入口、改变输入/参数、错误行为和科学结果，保存实际命令及所测试文件的哈希。构建者的 smoke check 只能支持已测路径；需要证据记录格式时读[调用与验证示例](../../references/method-tool-example.md)。

## 输出与验收

按[运行约定](../../references/runtime-contract.md)登记真实存在的工具入口、契约、实现版本、适用条件及限制。存在封装但尚未完成验证时最高为 `wrapped`；如果只是接口设计则保持 `documented` 并注明尚未实现。

将 wrapper 源码、依赖/调用说明与已有验证记录的真实文件或目录列入产物 `source_paths`，使用绝对路径或相对 `project_dir`；不要指向临时目录、全局环境或只留下 host 路径文字。`wrapped`、`tested`、`reproduced` 必须有可导出材料，纯 `documented` 可无。`_asset` 由协调器生成，不由本技能填写。

将实现方式、调用契约和验证范围写入 `code_tools` 的 schema 允许扩展字段或可定位的说明文件；不要只列工具名字。只有对应验证已运行且有证据时才升级为 `tested` 或 `reproduced`；复制 `source_paths` 只保全材料。

当前 `paper` worker 同时收到构建与验证 skill，这不构成独立验证。后续 `expert_review` 是独立的专家资产审查，可根据风险复验工具；只有审查者真正重新调用并记录结果，才能声明该范围经过独立复验。当前没有自动强制执行全部工具测试的独立阶段或 runner。
